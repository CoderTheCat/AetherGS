## 二、C1: Progressive Densify 分析

### 2.1 理论层面

**预期 +25% 的理论依据**：
- 假设：渐进式增加点数可以减少初期计算复杂度

- 参考：DashGaussian 论文宣称 45.7% 加速

**理论缺陷**：
1. **忽略了 LiteGS 已是速度 SOTA（50 秒）的事实**
   - DashGaussian 的 200 秒训练已被 LiteGS 超越
   - 在已经优化的系统上，进一步优化的空间有限

2. **理论模型过于简化**
   - 假设点数与训练时间线性相关
   - 实际上 LiteGS 已有 warp-based rasterization（13.4x 加速）
   - 渲染已不是唯一瓶颈

**核心实现**（`litegs/training/densify.py`）：

```python
@torch.no_grad()
def get_current_target(self, epoch: int) -> int:
    if epoch < self.densify_params.densify_from:
        return self.init_points_num
    if epoch >= self.densify_params.densify_until:
        return self.target_points_num
    progress = (epoch - self.densify_params.densify_from) / \
               (self.densify_params.densify_until - self.densify_params.densify_from)
    current_target = self.init_points_num + \
                     (self.target_points_num - self.init_points_num) * progress
    return int(current_target)
```

## 三、C2: Enhanced Frustum Culling 分析

### 3.1 理论层面

**预期 +20% 的理论依据**：
- 假设：添加 margin 可以减少边界闪烁，adaptive 策略可以动态调整剔除范围
- 推理：更智能的剔除 → 减少渲染的高斯点 → 加速
- 参考：视锥剔除在图形学中是成熟技术

**理论缺陷**：

1. **高估了剔除的潜在收益**
   - LiteGS 已有高效的 cluster-cull-compact 管线
   - 大部分不可见 cluster 已被剔除
   - 剩余可优化的空间有限

2. **margin 和 adaptive 策略缺乏理论支撑**
   - `margin=0.1` 是经验值
   - `adaptive_margin = margin * (1.0 + dist_to_camera * 0.1)` 中的 0.1 是 magic number

### 3.2 代码层面

**核心实现**（`litegs/utils/__init__.py`）：

```python
def frustum_culling_aabb_enhanced(frustumplane, aabb_origin, aabb_ext,
                                   margin=0.1, adaptive=True):
    dist_origin = (frustumplane[..., 0:3, None] * aabb_origin).sum(-2) + frustumplane[..., 3]
    dist_ext = (frustumplane[..., 0:3, None] * aabb_ext).abs().sum(-2)
    
    if adaptive:
        # 自适应策略：距离越远，margin 越大
        dist_to_camera = torch.norm(aabb_origin, dim=0, keepdim=True).unsqueeze(1)
        adaptive_margin = margin * (1.0 + dist_to_camera * 0.1)  # ⚠️ 0.1 是 magic number
        dist_ext = dist_ext + adaptive_margin
    else:
        dist_ext = dist_ext + margin
    
    culling = (dist_origin + dist_ext < 0).sum(dim=-1).transpose(0, 1)
    visibility = (culling == 0)
    return visibility
```

**实现问题**：

1. **自适应策略缺乏验证**
   - `dist_to_camera * 0.1` 的 0.1 系数没有理论依据
   - 没有根据场景特点动态调整

2. **额外计算开销**
   - 每帧计算 `torch.norm(aabb_origin, dim=0)`
   - 在 GPU 上这是额外开销

3. **未考虑 GPU 并行化**
   - 纯 PyTorch 实现
   - 没有 CUDA kernel 优化

## 四、C3: FP8 混合精度训练 分析

### 4.1 理论层面

**预期 +25% 的理论依据**：
- 假设：FP8 可以减少内存带宽，利用 Tensor Core 加速
- 推理：更低的精度 → 更快的计算 → 加速

**理论缺陷**：

1. **忽略了硬件兼容性**
   - FP8 Tensor Core 需要 Hopper 架构（SM 8.9+）
   - LiteGS 测试的 RTX 3090 (8.6) 和 RTX 4090 (8.9) 不支持真正的 FP8 Tensor Core

2. **混淆了 GradScaler 和 FP8 训练**
   - GradScaler 是 FP16 混合精度的工具
   - 真正的 FP8 需要 `torch.float8_e4m3fn` 类型和延迟缩放技术

**实现问题**：

1. **仅使用了 GradScaler**
   - 这是 FP16 混合精度的通用工具
